# 缺陷报告：NTP 时间差在系统时间恢复后仍被沿用

关联 Issue：#3006

## 问题摘要

在部分环境中，尤其是虚拟机刚重启后的早期阶段，主机本地时间可能还没有完成同步。如果 DataKit 在这个时间窗口内启动，它会从 DataWay 观测到一个很大的时间差，并把这个时间差缓存在当前进程中。

修复前，DataKit 只会在“观测到的时间差超过阈值”时更新这份缓存；如果后续主机时间已经恢复正常，新的时间差回到阈值内，旧缓存却不会被清零。这样一来，后续采集点仍会继续套用一份已经过期的时间偏移，直到 DataKit 进程重启。

## 用户可见现象

典型表现如下：

- 虚拟机重启后，DataKit 本地仍在持续采集数据。
- `/metrics` 中的 DataKit 自身指标持续增长。
- 写入 DataWay 的请求状态正常。
- 服务端界面在默认时间范围内看不到新数据，表现为断档。
- 等主机时间恢复后，再重启一次 DataKit，数据重新可见。

这类问题表面上像“上传成功但服务端没数据”，本质上是时间戳偏移问题。

## 触发条件

这个问题一般需要同时满足以下条件：

1. 主机在 DataKit 启动早期存在明显时间偏差。
2. DataKit 在这个阶段从 DataWay 读到了一个较大的时间差，并缓存下来。
3. 主机时间随后恢复正常，但 DataKit 进程没有重启。
4. 后续接近 0 的时间差没有清掉之前缓存的大偏差。

## 根因分析

根因在 `internal/ntp/ntp.go`。

修复前的行为是：

- 当观测到的时间差大于阈值时，更新进程内缓存。
- 当观测到的时间差恢复到阈值内时，不做任何处理。

而 `ntp.Now()` 在生成当前“校正后时间”时，会持续使用这份进程级缓存。因此，只要缓存里还保留着早期启动阶段的错误偏移，后续新产生的数据点就会继续被打到错误时间窗口。

这个问题与具体实现细节强相关，但文档不在这里展开代码，以免后续实现调整后文档失真。维护时优先关注：

- `internal/ntp/ntp.go`
- `internal/io/feed.go`

## 为什么重启 DataKit 可以恢复

因为这个错误偏移是进程级状态。

当主机时间已经恢复正常后再重启 DataKit：

- 旧的时间差缓存会随进程退出而消失。
- 新进程启动时不会再读到之前那个大的错误偏差。
- 后续数据就会重新落回正确的时间窗口。

所以用户看到的“重启 VM 后首次启动异常，再重启一次 DataKit 就恢复”，并不是采集链路恢复了，而是错误缓存被清掉了。

## 现场证据

这次问题的现场里有几个非常关键的信号：

1. 日志中出现了明显的大时间差更新，例如 `update local time diff 8h0m1s`。
2. `/metrics` 中可以看到 `/v1/write/metric` 等写入请求状态为 `OK`。
3. `/metrics` 中存在 `datakit_io_point_time_adjusted_total`，说明 DataKit 的时间修正逻辑确实被触发过。

这三个信号放在一起时，基本可以判断：

- 数据已经采到了。
- 数据也已经写出去了。
- 问题更可能出在数据时间落点，而不是链路传输失败。

## 修复思路

这次修复保持了原有阈值语义，只调整了恢复路径：

- 如果当前观测到的时间差仍然大于阈值，继续保留时间修正。
- 如果当前观测到的时间差已经回到阈值内，则清空旧的进程级缓存。

这样可以兼顾两点：

- 主机时间确实异常时，DataKit 仍然可以进行时间修正。
- 主机时间恢复正常后，DataKit 不会继续套用旧偏移。

## 回归测试

针对这个问题，在 `internal/ntp/ntp_test.go` 中补了回归测试，覆盖的核心场景是：

1. 先记录一个较大的时间差。
2. 再模拟主机时间恢复，时间差回到阈值内。
3. 验证进程级缓存被清零。
4. 验证后续的“当前时间”不再继续套用旧偏移。

## 后续排查建议

以后如果再遇到“DataKit 本地有采集，但服务端默认时间窗口内看不到数据”的问题，建议优先按下面顺序排查：

1. 查看 DataKit 日志里是否出现 `update local time diff ...`
2. 查看 `/metrics` 中 `/v1/write/*` 的状态是否正常
3. 查看 `/metrics` 中 `datakit_ntp_time_diff_*`
4. 查看 `/metrics` 中 `datakit_io_point_time_adjusted_total`
5. 结合主机是否刚重启、时间同步服务是否刚恢复来判断

如果上传状态正常，同时启动阶段又出现过较大的时间差，优先怀疑时间戳问题，而不是网络问题。

## 运维建议

虽然代码已经修复了“旧偏移不清零”的问题，但运维侧仍建议注意以下几点：

- 尽量让 DataKit 在主机网络和时间同步基本就绪后再启动。
- 对于启动后时钟收敛较慢的环境，重点观察启动早期的 `ntp` 日志。
- 当界面出现断档时，先对比“写入是否成功”和“时间窗口是否正确”，不要一开始就把排查方向放在 DataWay 链路上。
