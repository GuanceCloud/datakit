# Pipeline JIT release contract

Runtime configuration, rollback and current performance: [Pipeline JIT 配置与性能说明](pipeline-jit.md).

DataKit has two deliberately separate Linux build variants:

- The standard build does not use the `pipeline_jit` build tag. It remains a
  `CGO_ENABLED=0` static binary and supports both glibc and musl systems. If JIT
  is enabled in its runtime configuration, initialization reports that the
  native runtime is unavailable. Initial startup defaults to the Go executor
  when `pipeline.jit.on_init_error` is omitted or set to `"go"`; an explicit
  `"error"` returns the initialization error.
- The Pipeline JIT build uses the `pipeline_jit` tag on Linux amd64 and arm64.
  It loads `libplatypus_jit.so` through the system dynamic loader and therefore
  requires glibc. Other operating systems and Linux architectures continue to
  use the standard build even when a multi-platform release enables JIT.

The release builder selects the JIT variant only when all three variables are
provided:

```text
PIPELINE_JIT_ENABLED=1
PLATYPUS_JIT_RUNTIME_DIR=/path/to/platplusplus/dist/jit-runtime
PLATYPUS_JIT_EXPECTED_REVISION=<full platplusplus git revision>
```

Each supported architecture directory must contain:

```text
linux-amd64/
  libplatypus_jit.so
  libplatypus_jit.so.sha256
  manifest.json
linux-arm64/
  libplatypus_jit.so
  libplatypus_jit.so.sha256
  manifest.json
```

The manifest is generated by the platplusplus producer and has this schema:

```json
{
  "schema_version": 1,
  "source_revision": "40-or-64-character-hex-revision",
  "target": "x86_64-unknown-linux-gnu",
  "artifact": "libplatypus_jit.so",
  "sha256": "64-character-hex-digest",
  "runtime_abi": "pp-jit-flat-v1+ppr3+pps1",
  "profile": "pipeline-go-1.4.3-datakit"
}
```

For arm64, `target` is `aarch64-unknown-linux-gnu`. The DataKit builder fails
closed if the configured revision, manifest, checksum, ELF architecture, shared
object type, or required dynamic ABI symbols do not agree. It stages the
library, checksum, and manifest in the package's `lib` directory so a deployed
runtime can be traced back to its producer revision.

The repository does not guess a platplusplus URL or credentials. CI must import
the producer artifact through a trusted GitLab artifact/dependency mechanism
and point `PLATYPUS_JIT_RUNTIME_DIR` at the extracted directory. Leaving
`PIPELINE_JIT_ENABLED=0` produces the standard static release.
